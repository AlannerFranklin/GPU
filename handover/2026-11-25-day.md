## 二、最重要的一个设计决策：两个计数器用**相反**的聚合规则

**这是整个工具里唯一需要"想"而不是"抄"的地方，已写进代码注释：**

```
利用率 → 取 max
  3D 和 Copy 是【并行硬件】，可以同时干活。
  3D 40% + Copy 20% 不代表占了 60% —— 求和会超过 100%。
  取最大值 = 「最忙的那个引擎忙了多久」。

显存 → 求和
  同一进程在多块 GPU 上各占一份真实显存
  （实测 pid_12904 同时出现在 luid_0xAF9D 和 luid_0xB2EC 下）。
  加起来才是这个进程的总占用。
```

**Windows 没有官方文档明确说任务管理器怎么聚合**，所以这是**自己的设计决策**，
面试可以讲。

## 三、学员犯的错（4 个，全是「新概念第一次见」）

| # | 错 | 性质 |
|---|---|---|
| 1 | `PdhCloseQuery` 写在 `while` 循环**里面** | 资源释放位置错误——第一轮后查询就关了，后面用的是已关闭的句柄 |
| 2 | 少了循环外那次「建基线」的采样 | 第一帧数据无效（被 `util <= 0` 滤掉，表现为空表） |
| 3 | 新打印块**追加**，旧的没删 | 打两张表；且第 223/238 行重复声明 `wchar_t name[64]` → C2374 重定义 |
| 4 | `printf("\n")` 留在光标归位之后 | 表格每帧被顶下一行，第一行永远没人覆盖 → 顶部残字 |

**编译期错误两个（他都自己撞上了）：**

- `QueryFullProcessImageName` 报 `C2664`（wchar_t 转 LPSTR）
  → **A/W 后缀机制**：没定义 UNICODE 时，不带后缀的名字展开成 A 版。
  他随后在 CMakeLists 里加了 `-DUNICODE -D_UNICODE`（正规做法）。
- `std::max` 报 `C2589: "(" : "::" 右边的非法标记`
  → **`windows.h` 定义了 `min`/`max` 宏**，把 `std::max(...)` 展开成了
  `std::(((a)>(b))?a:b)`。解法：`#define NOMINMAX` 必须在 `#include <windows.h>` **之前**。

## 四、学员问的三个概念问题（都已答）

**① 「理论上不应该是四个句柄吗？」**

对。PDH 三个（1 个 query + 2 个 counter）+ 控制台的 `hOut` = 4 个。
但**只有 query 需要显式关闭**，两个 counter 随它释放，`hOut` 是系统对象不归你管。

**② 「windows 编程一窍不通，每个变量函数代表什么都看不懂」**

已系统讲过：四个基本类型对照表（DWORD/BOOL/LPCWSTR/HANDLE）、
HANDLE 的「句柄表」模型（是索引不是地址，不能解引用，要 Close）、
Win32 的「调用方准备缓冲」模式。

**③ 「为什么 map 里同一个 pid 会有两行？」**

那不是 map 的问题——是**上一帧的残字没被覆盖**。
`SetConsoleCursorPosition` 只移动光标、不清屏；新帧比旧帧短时，尾巴会留下。
解法：`FillConsoleOutputCharacterW` 从光标位置填空格。

## 五、一个有意思的现场观察（已讲）

```
13668  <unknown>    1.49%   170.5 MB
```

**占着 170 MB 显存，但 GPU 利用率只有 1.49%。**

这说明「显存占用」和「利用率」是**两个不同维度**——一个程序可以缓存了大量纹理
却几乎不算。**这也是为什么监控工具要看两个数，不能只看一个。**

**ETW 和 PDH 的区别（已预告）：**

| | PDH | ETW |
|---|---|---|
| 数据形态 | **当前值**（一个数） | **事件流**（带时间戳的记录） |
| 用法 | 每秒采一次 | **持续订阅**，事件来了就回调 |
| API | 5 个函数 | 会话管理 + 回调处理 |
| 权限 | 普通用户 | **内核 provider 要管理员** |

**ETW 能拿到 PDH 拿不到的东西**：「这个 kernel 什么时候开始/结束」、
「驱动在这个时刻做了什么」。
