|---|---|---|
| ① 四种语义 | ✅ | relaxed=只保原子不保序；release=封存之前；acquire=解封之后；seq_cst=acquire+release+全局唯一顺序 |

## ✅ 优先级 5：ncu 的 load efficiency（2026-11-21 完成）

**重要发现：`gld_efficiency` 是旧工具（nvprof / Nsight Visual Profiler）的指标名，
ncu 里不存在。** ncu 的对应指标是：

```
smsp__sass_average_data_bytes_per_sector_mem_global_op_ld.pct
```

（含义：global load 每个 sector 平均用到多少字节的百分比）

**已测结果（管理员终端）：**

| kernel | 指标值 | 与预期对比 |
|---|---|---|
| vector_add_strided | **12.50%** | 精确命中预测（4B/32B = 12.5%） |
| vector_add（合并版） | **100.00%** | 精确命中 |

**对照结论：100 / 12.5 = 8.0 —— 8 倍流量由 profiler 直接量出，不再是纸上推算。**

两轮 ratio：11.48 / 11.25，与 11-05 首次实测的 11.31 吻合。

**已讲清**：12.5% → 8 倍流量膨胀（1/0.125）；多出的 1.4 倍是请求排队损耗。

### ① 编译链路 ⚠️（顺序错）

学员答案："`.cu` → 机器码 → 汇编 → 链接"——**汇编与机器码顺序颠倒**，
且不知道 nvcc 的角色。

**正确链路（已讲）：**

```
.cu
 ├─ 预处理
 ├─ nvcc 拆分（nvcc 是【驱动程序】，自己不编译）：
 │    ├─ device 代码 → cicc 编译成 PTX → ptxas 汇编成 SASS → 打包进 fatbin
 │    └─ host 代码   → 交给 cl.exe（MSVC）编译成 .obj
 └─ 链接：host .obj + fatbin + CUDA 运行时库 → .exe
```

### ② 指针内存图 ❌（第二次错同一处）

**与 11-03 自检第 2 题错法完全相同**：`int (*p)[5]` 与 `int *p[5]` 互换。

| 声明 | 正确答案 | 学员答案 |
|---|---|---|
| `int** p` | 二级指针；sizeof=8 | "二维数组"，sizeof=8（数字对，定性错） |
| `int (*p)[5]` | **一个指针**指向 int[5]；sizeof=**8**，`*p`=20 | "5 个指针，40" ❌ |
| `int *p[5]` | **一个数组**，5 个 int*；sizeof=**40** | "数组，5×4=20" ❌ |

**根因（已点破）**：`int *p[5]` 的元素类型是 **`int*`（8 字节）**，不是 `int`（4 字节）——
把"元素类型"看成了 int，所以算出 5×4=20。

学员能背出规则"先看括号内，没有就先右后左"，但**没有执行最后一步**：
看到 `[5]` 先结合成数组后，要判断 `*` 修饰的是"元素"还是"p 本身"。

**复查安排**：下次必须能画出三者的内存图（不只是报 sizeof），并说出 `p+1` 各前进多少字节
（8 / 20 / 40）。这是第三次机会，再错就要专门做一组指针练习。

**学员决定（2026-11-21）**：指针图**下周末继续**。编译链路项随指针图一起复查。
