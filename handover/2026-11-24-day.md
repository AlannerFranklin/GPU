### 结果：一处语法错，其余全对

```cpp
C[row * N][col] = sum;      // ❌ C 是 float*，不能二次下标
C[row * N + col] = sum;     // ✅
```

| 位置 | 判定 |
|---|---|
| As 填 shared | ✅ `As[ty][tx] = A[(blockIdx.y*32+ty)*N + t*32 + tx]` |
| Bs 填 shared | ✅ `Bs[ty][tx] = B[(t*32+ty)*N + blockIdx.x*32 + tx]` |
| 两次 `__syncthreads()` 位置 | ✅ |
| 累加 | ✅ `sum += As[ty][k] * Bs[k][tx]` |
| block / grid | ✅ `dim3(32,32)` / `dim3(N/32, N/32)` |

**对比 11-23 下午**：昨天卡了一下午的两个下标（包括「B 的行下标要乘 N」），
今天一次全对。**坐标映射这一关确实过了。**

## 三、M4 第三项：判断题第二道 —— 暴露了一个新的模式

### 题目

```cpp
__global__ void poly_eval(float* in, float* out, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= N) return;
    float x = in[i];
    float y = 1.0f;
    for (int k = 0; k < 512; k++) {
        y = y * x + 0.5f;        // 512 次乘加
    }
    out[i] = y;
}
```

### 学员答案 vs 正确

| # | 问 | 学员答 | 判定 |
|---|---|---|---|
| ① | 每元素 FLOP | 1024 | ✅ |
| ② | 每元素 DRAM 字节 | 4 进 4 出 = 8 | ✅ |
| ③ | AI | `2N/8N = 0.25` | ❌ 应为 **128** |
| ④ | 落区 / 天花板 | 「带宽这边」 | ❌ **compute-bound**；天花板 = min(44,100, 672×128=86,016) = **44,100** |
| ⑤ | 能跑到天花板吗 | 「跑不到，卡在要读 x」 | ❌ 见下 |
| ⑥ | 怎么改 | 「把 x 放进 shared」 | ❌ 见下 |

### ③ 的关键错误：分子用错了

```
正确：AI = 1024N FLOP / 8N 字节 = 128
学员：AI = 2N / 8N = 0.25
```

**他把上一题（9 点模糊滤波）的模型套过来了**——那一题每个元素确实只做 2 次加法。
这一题每个元素做 **1024** 次。

> **AI 的分子是「这个 kernel 真正做了多少运算」，不是「读了多少个元素」。**

### ⑤ 的真正答案：两个可能，要看 SASS

**学员说「卡在要读 x」是错的**——`x` 只从内存读一次，进了寄存器，循环里 512 次都是寄存器操作。

真正的两个嫌疑：

1. **依赖链**：`y = y*x + 0.5` 每次都要等上一次的 `y`。FFMA 延迟约 4 周期，
   512 次串起来就是 2048 周期的纯等待
2. **指令配比**：这一行只有 1 条 `FFMA`，循环里还有 `k++`、比较、跳转。
   如果没充分展开，4 条指令里只有 1 条在算 → 算力利用率封顶 25%

**哪个是主因要看 SASS 和 ncu——这就是「判断」和「猜」的区别。**

### ⑥ 正确方向：拆依赖链，不是搬到 shared

x 已经在寄存器里，**没有任何重复的内存读**，搬 shared 只会更慢。

```cpp
// 现在：一条 512 长的串行链
for (int k = 0; k < 512; k++) y = y*x + 0.5f;

// 改成：4 条 128 长的独立链
float y0=1, y1=1, y2=1, y3=1;
for (int k = 0; k < 128; k++) {
    y0 = y0*x + 0.5f;
    y1 = y1*x + 0.5f;
    y2 = y2*x + 0.5f;
    y3 = y3*x + 0.5f;
}
```

**ILP 从 1 变成 4，延迟被藏住。**（数学结果会变，只是演示手法。真正做多项式求值
有经典解法叫 **Estrin 法**，就是把这个串行链改写成树形。）

**已强调：这和 matmul 里 16 个独立 `acc[i][j]` 是同一个思路。**

### 这道题要记住的一句话

> **compute-bound 不等于「算力用满了」。**
> 它只说明「天花板是算力定的」——能不能跑到，还要看指令配比、依赖链、occupancy。

**上一题是「带宽用满了但没法再优化」，这一题是「天花板很高但够不着」。两种都是常态。**

## 二、逐项排查的结果

| 技能 | 和 GPU 的关系 | 处置 |
|---|---|---|
| **ETW**（Event Tracing for Windows） | **直接**：GPU 驱动通过 ETW 发事件（`Microsoft-Windows-DxgKrnl`、`NVIDIA-Driver`）。**做 profiler 就是订阅这些** | 提到第 17 周 |
| **PDH**（Performance Data Helper） | **直接**：**任务管理器里 GPU 那一栏，底层就是 PDH**（`\GPU Engine(*)\Utilization Percentage`） | 提到第 17 周 |
| 进程枚举 / 句柄 | **直接**：监控工具要列出「哪些进程在用 GPU」，就要枚举进程、打开别人的句柄 | 第 18 周 |
| DLL 动态加载 | **直接**：CUDA / NVML / D3D 全是 DLL | 第 18 周 |
| 内存映射文件 | 间接（跨进程传大量性能数据） | 选做 |
| **IOCP** | **基本无关**——那是「高并发网络服务器」的技能 | **移出** |
| **Windows 服务** | 弱相关 | 选做 |

**IOCP 是原计划里最不相关的一项。** 它来自门 A 时代 JD 里的
「Linux 进程/线程/IPC/socket」——但那是 Linux，而且是驱动岗的要求，不是性能工程岗的。
