## 三、M4 第三项：判断题第二道 —— 暴露了一个新的模式

### 题目

```cpp
__global__ void poly_eval(float* in, float* out, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= N) return;
    float x = in[i];
    float y = 1.0f;
    for (int k = 0; k < 512; k++) {
        y = y * x + 0.5f;        // 512 次乘加
    }
    out[i] = y;
}
```

### 学员答案 vs 正确

| # | 问 | 学员答 | 判定 |
|---|---|---|---|
| ① | 每元素 FLOP | 1024 | ✅ |
| ② | 每元素 DRAM 字节 | 4 进 4 出 = 8 | ✅ |
| ③ | AI | `2N/8N = 0.25` | ❌ 应为 **128** |
| ④ | 落区 / 天花板 | 「带宽这边」 | ❌ **compute-bound**；天花板 = min(44,100, 672×128=86,016) = **44,100** |
| ⑤ | 能跑到天花板吗 | 「跑不到，卡在要读 x」 | ❌ 见下 |
| ⑥ | 怎么改 | 「把 x 放进 shared」 | ❌ 见下 |

### ③ 的关键错误：分子用错了

```
正确：AI = 1024N FLOP / 8N 字节 = 128
学员：AI = 2N / 8N = 0.25
```

**他把上一题（9 点模糊滤波）的模型套过来了**——那一题每个元素确实只做 2 次加法。
这一题每个元素做 **1024** 次。

> **AI 的分子是「这个 kernel 真正做了多少运算」，不是「读了多少个元素」。**

### ⑤ 的真正答案：两个可能，要看 SASS

**学员说「卡在要读 x」是错的**——`x` 只从内存读一次，进了寄存器，循环里 512 次都是寄存器操作。

真正的两个嫌疑：

1. **依赖链**：`y = y*x + 0.5` 每次都要等上一次的 `y`。FFMA 延迟约 4 周期，
   512 次串起来就是 2048 周期的纯等待
2. **指令配比**：这一行只有 1 条 `FFMA`，循环里还有 `k++`、比较、跳转。
   如果没充分展开，4 条指令里只有 1 条在算 → 算力利用率封顶 25%

**哪个是主因要看 SASS 和 ncu——这就是「判断」和「猜」的区别。**

### ⑥ 正确方向：拆依赖链，不是搬到 shared

x 已经在寄存器里，**没有任何重复的内存读**，搬 shared 只会更慢。

```cpp
// 现在：一条 512 长的串行链
for (int k = 0; k < 512; k++) y = y*x + 0.5f;

// 改成：4 条 128 长的独立链
float y0=1, y1=1, y2=1, y3=1;
for (int k = 0; k < 128; k++) {
    y0 = y0*x + 0.5f;
    y1 = y1*x + 0.5f;
    y2 = y2*x + 0.5f;
    y3 = y3*x + 0.5f;
}
```

**ILP 从 1 变成 4，延迟被藏住。**（数学结果会变，只是演示手法。真正做多项式求值
有经典解法叫 **Estrin 法**，就是把这个串行链改写成树形。）

**已强调：这和 matmul 里 16 个独立 `acc[i][j]` 是同一个思路。**

### 这道题要记住的一句话

> **compute-bound 不等于「算力用满了」。**
> 它只说明「天花板是算力定的」——能不能跑到，还要看指令配比、依赖链、occupancy。

**上一题是「带宽用满了但没法再优化」，这一题是「天花板很高但够不着」。两种都是常态。**

## 二、typeperf：先看到真实数据（不写代码）

```bat
typeperf -qx "GPU Engine"                                    :: 列所有计数器路径
typeperf "\GPU Engine(*)\Utilization Percentage" -sc 5        :: 实时采样 5 次
```

**坑**：`typeperf -q "\GPU Engine(*)"` 会报「找不到指定的对象」——
`-q` / `-qx` 的参数是**对象名**，不是带通配符的路径。正确写法是 `-qx "GPU Engine"`。

**学员的输出显示**（有价值，已讲解）：
- 两个 LUID（`0xAF9D` / `0xB2EC`）= 两块适配器（核显 + 虚拟显示适配器）
- 每块 13 个引擎：`3D` / `Copy` / `VideoDecode` / `VideoProcessing` / 空类型
- **实例名本身就是迷你数据库**：`pid_XXX_luid_XXX_phys_N_eng_N_engtype_XXX`

**已强调的坑**：这个百分比**不是「整卡利用率」**，而是「这个进程的这个引擎」的利用率。
任务管理器的聚合方式是「每引擎取进程最大值，再对引擎取最大值」——**不是求和**。
**自己的工具要自己定义聚合方式，并写进 README**（这本身是可讲的设计决策）。

## 三、从零写第一个 PDH 程序 —— 学员第一次接触 Windows API

新建 `code/19-gpu-monitor/pdh_demo.cpp`（纯 C++，不涉及 CUDA）。

### 教学上的关键决定

学员说「我对这个 windows 编程一窍不通，每一个变量函数代表什么都看不懂」。

**没有直接给代码，而是先讲清了四个基本类型和 HANDLE 的本质**：

| 名字 | 实际是 | C++ 里的对应 |
|---|---|---|
| `DWORD` | 32 位无符号整数 | `uint32_t` |
| `BOOL` | 32 位整数 | `int` |
| `LPCWSTR` | 宽字符串指针 | `const wchar_t*` |
| `HANDLE` | **内核对象句柄** | `void*`，但**不能解引用** |

**HANDLE 的讲解**（这是 Windows 编程唯一的新概念）：
内核维护一张句柄表，`OpenProcess` 返回的是表里的索引，不是内存地址。
`CloseHandle` = 引用计数 -1。不关就是句柄泄漏（漏的是内核资源）。

**「谁分配缓冲」的规矩**：Win32 API 固定模式是「调用方准备，被调方填充」，
因为函数不能返回局部数组。

### 学员犯的错

**第一版**：遍历那段写对了（`wcsstr` 找 `pid_`、`wcschr` 找 `)`、算长度、`wcsncpy_s`），
**第一次写 Windows API 能到这个程度不错**。但漏了第二次采样。

**第二版 `process_name`**：五个错
1. 没有 `return`（函数声明要返回 `const wchar_t*`）
2. `OpenProcess` 没检查 `nullptr`
3. `QueryFullProcessImageName` 没检查返回值
4. `buf` / `bufSize` 一个都没用
5. 没从完整路径里取文件名

**还有第六个，在调用处**：`process_name(pid, buf, bufSize)` —— **把 PDH 的数据缓冲当成了进程名缓冲**。
两个完全不同的缓冲同名，混了。

### 编译错误：A/W 后缀

```cpp
QueryFullProcessImageName(h, 0, path, &size);
// error C2664: 无法将参数 3 从 wchar_t[260] 转换为 LPSTR
```

**原因**：所有涉及字符串的 Win32 API 都有两个版本（`FooA` 窄字符 / `FooW` 宽字符），
头文件用 `UNICODE` 宏决定不带后缀的名字展开成哪个。
本项目没定义 `UNICODE` → 展开成 A 版 → 和 `wchar_t` 类型不匹配。

**其他几个调用没报错**，因为代码里显式写了 `W`（`PdhOpenQueryW` 等）。

**修法**：① 显式写 `QueryFullProcessImageNameW`（采用）② 或 CMake 里 `add_definitions(-DUNICODE -D_UNICODE)`。

**已作为通用规矩讲清**：要么全局定义 UNICODE，要么每个调用显式写 W，**不要混**。

### ⭐ 一个重要的教学事故（AI 自己的错）

第三道题第一版，我给的 ncu 数据是 `dram_bytes = 34 GB`（比纸面 134 MB 大 254 倍）。

**学员从这组数据推出了正确的结论**（缓存命中低 → memory-bound），
**但我给的数字本身不自洽**：blockDim=256 时一个 block 的工作集只有 767 个 float = 3 KB，
L1 有 128 KB，缓存必然接得住，**根本不可能产生 34 GB 流量**。

**已当面认账，并把这个失误变成了更好的考点：**

> **看到「和计算差 254 倍」这种数字，第一反应不该是猜原因，
> 而该是「先验算这个数字自不自洽」。一个自洽不了的数据，说明前面的假设错了。**

然后换成真正会出问题的模式（`in[i*32]` 的 sector 浪费），重新出题。
