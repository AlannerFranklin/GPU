## 二、softmax：第 16 周七个 kernel 里唯一缺的

新建 `code/18-softmax/`：`softmax.cu` + `softmax_common.h` + `CMakeLists.txt`。

### 设计

```
一个 block 处理一行，grid = M（行数），block = 256
三次遍历：求 max → 求 Σexp(x-max) → 写回 exp(x-max)/s
```

**为什么减最大值**（已讲）：`exp(90) = 1.2e39` 超过 float 上限 3.4e38，直接算会 `inf/inf = NaN`。
减掉最大值后 `x_i - m ≤ 0`，`exp ≤ 1`，不会溢出；数学上分子分母同除 `exp(m)` 抵消，结果不变。

### 两个辅助函数（学员写，六处错已改）

```cpp
__device__ float block_sum(float v, float* buf);
__device__ float block_max(float v, float* buf);
```

**学员犯的错（按四步对照）：**

| 步骤 | 错 | 后果 |
|---|---|---|
| 1 warp 内归约 | 加了 `if (threadIdx.x < 32)` | 只有 warp 0 在归约，warp 1-7 的 224 个值全丢 |
| 1 | `off > 1` | 少了 `off=1` 那轮，只剩偶数下标之和 |
| 2 lane 0 写 shared | `buf[blockIdx.x]` | 越界（buf 只有 32 格），应为 `buf[warp]` |
| 3 warp 0 归约 | 没加 `if (warp == 0)` | 8 个 warp 重复做同一件事（结果相同，碰巧不错，但是浪费） |
| 3（max 版） | 中性元用 `0.0f` | 求 max 的中性元必须是 `-INFINITY`；输入全负时最大值会算成 0 |
| — | 两个函数定义在使用之后 | C++ 要求先声明后使用，编译错误 |

**`block_sum` 改对了，`block_max` 一个字没改**——已让学员对照 `block_sum` 重改。

### 学员当天问的三个概念问题（已讲）

**① `__global__` vs `__device__`**

| | 谁调用 | 能返回值 |
|---|---|---|
| `__global__` | host 启动 | ❌ void |
| `__device__` | device 函数调用 | ✅ |

「`__global__` 是入口，`__device__` 是帮手。」

**② 「这个代码和 `reduction_exam` 不相似」**

对，因为 **`block_sum` 是 `reduction_exam` 的进化版——它把整棵 shared 树干掉了**：

```
reduction_exam:  tile[256] → shared 树 8 轮 → warp shuffle 5 步 → tile[0]
block_sum:       v（寄存器里）→ warp shuffle 5 步 → buf[warp] → warp 0 再 3 步 → buf[0]
```

少了整个 shared 阶段，所以只有 20 来行。

**③ 「`__shfl_down_sync` 就是做线程间加法吗？那 max 怎么能用？」**

**关键纠正：`__shfl_down_sync` 不做任何运算，它只把值搬过来。**

```cpp
v += __shfl_down_sync(0xffffffff, v, off);            // 搬 + 自己加
v = fmaxf(v, __shfl_down_sync(0xffffffff, v, off));   // 搬 + 自己比大小
```

**通用原则：归约 = 通信 + 合并。** shuffle 管通信，合并算子由你定
（`+` / `fmaxf` / `fminf` / `*` / `&` 都行，只要满足结合律）。

**为什么 off 每次减半**：每步之后每个线程代表的元素个数翻倍。
32 个元素需要 2^k ≥ 32 → 5 步（16, 8, 4, 2, 1）；8 个 warp 需要 3 步（4, 2, 1）。

### harness（`softmax_common.h`）

和前面几个的差别：**输出是一片，不是标量**。两个检查：

| 检查 | 范围 | 判据 | 意义 |
|---|---|---|---|
| **每行总和 = 1** | 全部 16384 行 | < 1e-3 | **不依赖参考实现**，softmax 的定义性质 |
| 逐元素 | 抽 64 行 | < 1e-5 | 和 CPU 参考比 |

**造数据刻意取 [-30, 90]**：`exp(90)` 溢出 float。kernel 若忘了减 max 会直接出 NaN，
`row_sum` 立刻 FAILED——**这是个内置的陷阱检测**。

规模 M=16384 × N=1024 = 64 MB > L2 的 48 MB，测的是真 DRAM。

### 加了 `__syncthreads()` 消一个理论竞态

`m = block_max(m, buf)` 之后、`block_sum` 之前加一次同步：
`block_max` 结尾所有线程要读 `buf[0]`，而 `block_sum` 一开始就会覆盖它。
实际不会撞（中间隔着一整轮 expf），但形式上缺同步。

## 二、读 SASS（`docs/sass-analysis.md`）

用 `cuobjdump -sass` 反汇编四个 matmul 版本，统计关键指令：

| kernel | FFMA | LDS | 每 FMA 的 load | 设计值 |
|---|---|---|---|---|
| naive | 29 | — | **2.00**（58 LDG） | 2.0 ✅ |
| tiled | 32 | 40 | 1.25 | 2.0 |
| reg 4×4 | **512** | **160** | **0.31** | 0.5 |
| reg 8×8 | **2048** | **320** | **0.156** | 0.25 |

**发现：4×4 和 8×8 比设计值还低——编译器把 As 的读取向量化了。**

```
128 条 LDS（一次 1 个 float）
 32 条 LDS.128（一次 4 个 float）← 32×4 = 128，正好是全部 As 的读取量
```

因为 `As[r][k]` 与 `As[r][k+1]` 在 shared 里相邻。`Bs[k][tx+j*32]` 没被向量化
（k 连续时隔 128 字节）。**源码里的 0.5 在机器上实际是 0.31，只有读 SASS 才知道。**

另外确认：`if` 编译成谓词（`@!P1`）不是分支；无 `LDL`/`STL`（与 ptxas 的 spill 0 一致）；
`.reuse` 是操作数缓存标记。

## 三、tiled matmul：从零推导（不是背的）

**方法变了**：不再「讲设计 → 照着写」，改成「从已知问题出发，让他自己走到答案」。

四个问题一路问下来：

```
① 算一个 C 元素要读多少次？         → 2 × 4096 = 8192
② N=4096 时总共多少条 global load？  → 2^37 = 1.37e11
③ A 和 B 一共多少个数？              → 2 × 2^24 = 2^25
④ ②÷③ 等于多少？                     → 4096 = N
```

**第四问的答案就是 tiled 的全部理由：每个数据被重复读了 N 次。**

然后他自己说：「把重复读取的数据放到 shared memory 中读取。」

接着引导：
- 一个 block 算 C 的 32×32，需要 A 的 32 行全部列 + B 的全部行 32 列 = 1 MB
- shared 只有 48 KB → 装不下，差 21 倍
- **他算出 `32*32*2*4 = 8 KB`** ——正好是「只装 32 列」的大小
- 于是 k 方向切段，128 轮
- 他自己答出「填完一次同步、读完一次同步」

### 坐标映射：用 N=4 手算才通

学员反复卡在「行列 vs blockIdx/threadIdx」。**关键突破是让他手算 N=4 的完整例子**：

```
A = B = [[1..4],[5..8],[9..12],[13..16]]
block(2,2)，grid(2,2)

C[1][2]：blockIdx=(1,0)，threadIdx=(1,0)
  t=0：As[1][0]=A[1][0]=5, As[1][1]=A[1][1]=6, Bs[0][0]=B[0][2]=3, Bs[1][0]=B[1][2]=7
       sum = 5×3 + 6×7 = 57
  t=1：As[1][0]=A[1][2]=7, As[1][1]=A[1][3]=8, Bs[0][0]=B[2][2]=11, Bs[1][0]=B[3][2]=15
       sum = 57 + 77 + 120 = 254
  naive 版也是 254 ✅

然后让学员独立验 C[3][1]：blockIdx=(0,1)，threadIdx=(1,1) → 484，两种方式一致 ✅
```

**这是两周来第一次反向映射一次做对**（之前那个坐标专题卡了两天）。

### 学员犯的七个错（写代码时）

| 错 | 后果 |
|---|---|
| `#include <matmul_common.h>` 用尖括号 | 找不到本地头文件 |
| CMakeLists 没加目标 | 没编（`ninja: no work to do`） |
| `dim3(256)` / `dim3(32)` | 二维结构塌了，`threadIdx.y` 恒为 0 |
| `As[blockIdx.y*32 + ty][tx + t*32]` | **越界 127 倍**（As 只有 32×32） |
| `Bs[ty + 32*t][blockIdx.x*32 + tx]` | 同上 |

**核心概念**（已讲透）：

> **`As`/`Bs` 是 shared memory，属于「这个 block」，下标永远只有 `threadIdx`，
> 一个 `blockIdx` 都不能有。**
> **`A`/`B` 是 global memory，下标才是全局坐标。**

**修正后编译**：`Used 36 registers, 8192 bytes smem` —— **和原版 `matmul_tile` 完全一致**，
是「写对了」的最硬证据。

# 深夜补记：调整 3 —— 主线从「驱动」改成「性能工程」

## 一、另一个 AI 的批评（第三条，也是最准的）

> 「方向调整是对的，但主线选『驱动』选错了——那是一个你存量为 0 的赛道。」

### 它说对的地方

**① 调整 1 把四样东西混成了一个「主线」**

原话是「驱动 / SDK / 工具链 / 性能工具」，但这四样的存量差别巨大：

| 候选 | 存量 | 依据 |
|---|---|---|
| 驱动开发（KMD/UMD） | **5%** | DRM / PCIe / 中断处理，一行没写过 |
| SDK / 工具链 | 30% | 有 C++ 和工具开发，但没碰过 GPU SDK |
| **性能工程（kernel + profiling + 工具）** | **70%** | 6 个 kernel + SASS + Roofline + ncu |
| 算子优化专家 | 25% | 8 个月不够 |

**混在一起说，会误导后续周计划。**

**② 「国产原厂软件栈 HC 高一个数量级」没有出处**

AI 自己承认这是未核实的断言。更可信的判断是：
**国产 GPU 的命门是生态兼容，所以算子/框架适配的人多于驱动的人。**

**③ 「社招不考白板」说得太绝对**

面 CUDA 岗大概率还是会考。降级可以，但不能写成「基本不考」。

**④ 「先跳沾边公司」被低估了**

原文把它排在「第三条弥补路径」，但如果自动驾驶/工业视觉的 GPU 加速岗能给 25-35w，
**那它本身就是终点，不是跳板。**

**⑤ 开源起点反了**

`cuda-samples` 的 PR 基本是 typo 级别，价值接近 0。正确顺序：
**PaddlePaddle（国产框架、算子适配、PR 易合）→ CCCL/CUB → Vulkan-Loader**。

## 二、调整 3 的内容

```
新主线：性能工程 = 写 kernel + 会 profiling + 能做工具
```

**对应岗位（按优先级）：**

| # | 岗位 | 说明 |
|---|---|---|
| 1 | 自动驾驶 / 工业视觉 / 医疗影像的模型部署与 GPU 加速 | 池子最大，25-35w 能拿 |
| 2 | 国产原厂性能工具 / profiler 团队 | 少量但高度对口 |
| 3 | 推理加速（TensorRT / ONNX） | 通用 |
| 4 | 国产原厂 SDK / 工具链 | 可以投 |
| — | ~~驱动开发~~ | 零星机会看到就投，不作为准备方向 |

**连带修正三处：**

1. **闭卷底线保住**：reduction 和 matmul 必须能闭卷写（已过关，别丢）；内存序保留；MyVector 降级
2. **L1/L2 从「可选」回到主线**——「模型部署与加速」是最大池子，L1/L2 是入场凭证
3. **开源起点换成 PaddlePaddle 第一**
