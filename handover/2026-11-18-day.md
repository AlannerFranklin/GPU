## 一、前缀和：概念

```
输入 a  = [3, 1, 7, 0, 4, 1, 6, 3]

包含式  = [3, 4, 11, 11, 15, 16, 22, 25]
排除式  = [0, 3, 4, 11, 11, 15, 16, 22]      ← CUDA/Blelloch 默认做这个
```

用途：stream compaction、radix sort、并行分区。面试高频。

**为什么并行难**：每个输出依赖它前面的所有输入，看起来天然串行。三条路的复杂度：

| 算法 | 工作量 | 深度 |
|---|---|---|
| 串行 | O(n) | O(n) |
| Hillis-Steele | O(n log n) | O(log n) |
| **Blelloch** | **O(n)** | O(log n) |

Blelloch 是唯一「工作量不增加」的并行算法，代价是要扫两遍（上扫 + 下扫）。

## 二、上扫（up-sweep）—— 就是归约那棵树

用 8 个元素 `[3,1,7,0,4,1,6,3]`：

```
d=1:  a[1]+=a[0]→4   a[3]+=a[2]→7   a[5]+=a[4]→5   a[7]+=a[6]→9
      [3, 4, 7, 7, 4, 5, 6, 9]

d=2:  a[3]+=a[1]→11  a[7]+=a[5]→14
      [3, 4, 7, 11, 4, 5, 6, 14]

d=4:  a[7]+=a[3]→25
      [3, 4, 7, 11, 4, 5, 6, 25]
```

**通用规则（已让学员记）：**

```
第 d 层：所有满足 (i + 1) % (2d) == 0 的位置 i，执行 a[i] += a[i - d]
每过一层，活跃位置减半
```

**学员答 16 元素的第一版：层数 4 ✅，但第二层只列了 2 对（9+11、13+15），漏了（1+3、5+7）。**
完整应是 4 对：(1,3)、(5,7)、(9,11)、(13,15)。

## 三、下扫（down-sweep）—— 交换再加

先把根清零（`a[n-1] = 0`），这一步是算法的灵魂：**树根的「总和」换成了「前面的总和」**。

然后 d 从 n/2 降到 1，每对 `(i1, i2) = (i + d - 1, i + 2d - 1)`：

```
t       = a[i1]
a[i1]   = a[i2]
a[i2]   = t + a[i2]
```

8 元素走一遍（上扫后是 `[3,4,7,11,4,5,6,25]`）：

```
清零根：  [3, 4, 7, 11, 4, 5, 6, 0]

d=4 (3,7)：t=11; a[3]=0; a[7]=11+0=11
          [3, 4, 7, 0, 4, 5, 6, 11]

d=2 (1,3)：t=4;  a[1]=0;  a[3]=4+0=4
    (5,7)：t=5;  a[5]=11; a[7]=5+11=16
          [3, 0, 7, 4, 4, 11, 6, 16]

d=1 (0,1)：t=3;  a[0]=0;  a[1]=3
    (2,3)：t=7;  a[2]=4;  a[3]=11
    (4,5)：t=4;  a[4]=11; a[5]=15
    (6,7)：t=6;  a[6]=16; a[7]=22
          [0, 3, 4, 11, 11, 15, 16, 22]   ✅
```

学员推 16 元素的第一层时，结构答对（对子是 (7,15)、`a[7]=0`、`a[15]=旧a[7]+0`），
但把 8 元素例子里 `a[3]=11` 那个数搬过来了。**提醒：换规模时要换数据。**

## 五、scan_v0 的实现要点

```cpp
constexpr int TILE = 256;
__global__ void scan_v0(float* a, float* out, int N) {
    __shared__ float tile[TILE];
    const int n = TILE;
    tile[threadIdx.x] = a[blockIdx.x * n + threadIdx.x];
    __syncthreads();
    // 上扫 d=1,2,4,...  每层一次 __syncthreads，且必须在 if 外面
    // tile[n-1] = 0; __syncthreads();
    // 下扫 d=n/2,...,1
    out[blockIdx.x * n + threadIdx.x] = tile[threadIdx.x];
}
```

### 5.1 学员犯的三个错

| 错 | 后果 |
|---|---|
| 上扫/下扫动的是 `a`（global）不是 `tile`（shared） | **所有 block 都在写同一个全局地址** `a[n-1]=0`，跨 block 破坏数据；且 shared 完全没参与计算 |
| `n` 用了传进来的参数 N | 在 256 个元素的 shared 数组上跑 d 到 10,485,760 的循环，直接越界。**kernel 里的 n 是「每 block 多少」（256），不是数组总量** |
| `run_benchmark(scan_v0 dim3(256), ...)` | 少一个逗号 |

### 5.2 `__shared__` 大小必须是编译期常量（学员主动问的）

他问「`__shared__ float tile[256]` 是不是也该写成 `n`」。答：

**不能。** `blockDim.x` 是 launch 时才有的值，而 shared 片区必须在 kernel 启动前就分配好。
静态 shared 数组只能写常量表达式。

（真要用运行时大小得 `extern __shared__ float tile[];` + `<<<grid, block, 字节数>>>`，
即动态 shared memory。）

但**他的直觉抓到了真问题**：`dim3(256)` 和 `tile[256]` 是两个真相源，靠人肉保持一致。
解法是抽一个 `constexpr int TILE = 256;`，三处（数组声明、`n`、main 的 dim3）都用它。

**规则已立：凡是「每 block 处理多少」的地方，一律用常量，不写裸数字。**

## 六、scan v0 是「分段前缀和」，不是全局

每个 block 只扫自己那 256 个，**block 之间不传递**：

```
block 0 输出：[0, a0, a0+a1, ...]                正确
block 1 输出：[0, a256, a256+a257, ...]          ← 少了 a0..a255 的和
```

`scan_common.h` 的对拍按同样分段写（每 chunk 独立算排除式），所以 v0 能过。

**要让 block 1 也正确，需要第二遍：把前面所有 block 的总和加回来。** 那是 scan_v1。

## 七、scan_common.h 与 reduction_common.h 的差别

| | reduction | scan |
|---|---|---|
| 输出大小 | `grid.x`（或 1） | **`N`** |
| 对拍方式 | 全加成一个标量比 | **逐元素比** |
| memset | 需要 | 不需要（全覆盖写） |

## 七·补：scan v1（两遍法）与 v2（Hillis-Steele）

### v1：三个 kernel 解决「block 之间不传递」

```
scan_v1_local   <<<nBlocks, 256>>>   本地 Blelloch scan + 记录本块总和
scan_v1_offsets <<<1, nBlocks>>>     对 block_sums 做 exclusive scan（单 block）
scan_v1_add     <<<nBlocks, 256>>>   out[i] += block_sums[blockIdx.x]
```

**三次启动必须包进同一个计时窗口**：`Record(start)` → 三个 launch → `Record(stop)`。
kernel launch 是异步的，三个 kernel 在同一条流里按序执行，`stop` 排在最后，
所以 `ElapsedTime` 拿到的就是三段之和。**中间绝不能插 `cudaMemcpy` 或同步。**

**对拍方式必须跟着变**：v0 是「每 256 个分段算一次」，v1 的输出是**全局**前缀和，
参考要从头扫到尾。这是 v1 相对 v0 的实质变化。

**规模改为 N = 262144**（= 256 × 1024），这样 `nBlocks = 1024`，
`scan_v1_offsets` 才能用一个 block（1024 线程）扫完。

**学员犯的六处：**

| 位置 | 错 | 后果 |
|---|---|---|
| `scan_v1_local` 读入 | `a[threadIdx.x + blockDim.x * n]` | `blockDim.x*n` 是常量 65536，所有 block 读同一段 |
| `scan_v1_local` 写出 | 同上（第一次改漏了） | 所有 block 写同一段 |
| `scan_v1_offsets` 的 n | `const int n = TILE` | 树的大小应是 nBlocks |
| 读入下标 | `block_sums[threadIdx.x + blockDim.x * n]` | 单 block 直接 `block_sums[threadIdx.x]` |
| 多了「记录块总和」那步 | 那是 kernel 1 的事 | — |
| 缺写回 | 扫完没写回 `block_sums` | kernel 3 读不到偏移 |

**另一个隐患已发现并修复**：`scan_v1_offsets` 启动时 block 写死 1024，
如果 `nBlocks < 1024` 就越界读写 `block_sums`。改为 `<<<1, nBlocks>>>`。
学员第一次只改了计时那一处，预热那处漏了——**同一个 kernel 的两次启动必须一致**。

### v2：换成 Hillis-Steele + warp shuffle

| | Blelloch | Hillis-Steele |
|---|---|---|
| 工作量 | O(n) | O(n log n) |
| 层数 | 2 log n（上扫 + 下扫） | **log n** |
| 实现 | shared 树 | **warp shuffle** |

```cpp
for (int off = 1; off < 32; off *= 2) {
    float y = __shfl_up_sync(0xffffffff, x, off);   // 先读旧值
    if (lane >= off) x += y;                         // 再写回
}
```

**两个要点已讲：**
1. **同一层内必须用旧值**——所以先 `shfl` 读、后 `+=` 写
2. `if (lane >= off)` 不能少，warp 边界外的值是垃圾

**block 级四层**：warp 内 scan → lane 31 写 `warp_sums[warp]` → 串行扫 8 个 warp 总和
→ `x += warp_sums[warp]`。

**学员犯的五处：**

| 位置 | 错 | 后果 |
|---|---|---|
| `TILE` | 写成 1024 | 32 个 warp 但 `warp_sums` 只有 8 格，越界 |
| 循环上界 | `off < n`（n=256） | `off ≥ 32` 时 `__shfl_up_sync` 行为未定义 |
| 串行扫描 | `t = warp_sums[k]` 少 `float` | 编译错误 |
| 块总和 | `x + warp_sums[7]` | 把 warp 0-6 的和加了两次 |
| 块总和 | 没加 `if (threadIdx.x == TILE-1)` | 256 个线程竞争写同一个位置 |

**块总和的正确来源**：`x += warp_sums[warp]` 之后，**线程 255 的 x 就是整块总和**，
不需要另外算——因为 `warp_sums[]` 那时已经被覆盖成 exclusive 前缀，原始总和已经没了。

### 技术债：两个辅助 kernel 复制了三份

`scan_v1_offsets` / `scan_v1_add` 在 v1、v2 里各有一份，v3 还会再有一份。

**处理方式（和 matmul 那次一样）：先让功能对齐，再重构。**
v3 写完后抽到 `scan_kernels.h`，三个 `.cu` 一起 include。

### v3 的计划调整

原计划 v3 = 单 kernel（decoupled look-back，CUB 的做法）。**已改为只讲概念、不写实现**，
理由三条：

1. 今晚已积压 10 个没跑过的 kernel，再加最难的会分不清是谁的锅
2. 涉及内存序（`__threadfence()` + volatile 轮询），错一次能查一天
3. **公司机跑不了，写了等于白写**——这类算法不跑根本不知道对不对

**decoupled look-back 的流程已讲（面试可答）**：每块算本地 scan 和总和 → 发布聚合值 →
回头看前辈的聚合值 → 遇到「前缀就绪」的块就停 → 得到偏移后自己也发布「前缀就绪」。

**v3 改为「每线程 4 个元素」**，思路：线程内串行 scan → 用 `x[3]` 做 warp scan →
用 `__shfl_up_sync(..., carry, 1)` 转成排斥式 → 加回。

⚠️ **已留给学员的问题（v3 动手前要先答）**：`TILE` 在 v3 里还能是 256 吗？
256 线程 × 4 元素 = 1024，如果 TILE 仍是 256，`a[blockIdx.x*TILE + threadIdx.x*4 + i]`
会越界到什么程度？

**十个程序，两批输出。** 注意 scan 用的 N 是 262144，**不是 10485760**——

| 优先级 | 检查什么 |
|---|---|
| ① | 七个归约的 `rel_err` 全部 < 1e-3 |
| ② | `scan_v0` 打印 `scan check: OK`；`scan_v1` / `scan_v2` 打印 `bad_count=0` |
| ③ | 十个 `min_ms` 画曲线（**归约和 scan 规模不同，不可横向比**） |

**已知今晚大概率出问题的地方：**

- `reduction_v1`：`__syncthreads()` 是否真在 `if` 外（若挂死就是它）
- `reduction_v3`：写回有没有重复（结果小约 64 倍就是残留行）
- `reduction_v5/v6`：`warp_sums` 是否被写过（没写则 `rel_err` ≈ 1.0）
- `scan_v0`：改为 `tile` 之后是否还有遗漏的 `a`
