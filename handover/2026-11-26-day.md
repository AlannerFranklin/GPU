## 一、判断题第四道：**从「算 AI」改成「读 ncu 报告」**

前三道都是「给 kernel，算 AI」。**这道反过来**：给一份 ncu 报告，判断瓶颈在哪一层。

```
Duration                  3.21 ms
Compute (SM) Throughput   18.4%
DRAM Throughput            8.7%
L1/TEX Cache Throughput   81.3%
L2 Cache Throughput       35.2%
Achieved Occupancy        95.6%
Registers Per Thread         32
Shared Memory Per Block       0
```

**学员 ①② 答对（不是 DRAM 瓶颈、不是算力瓶颈），③ 卡住**——
「Shared Memory = 0，为什么 L1 81% 忙？」

**已讲清**：L1/TEX **不只是 shared memory 的容器**，它是**所有 global load 的必经之路**。
`Shared = 0` 只说明没用 shared，不代表 L1 闲着。

**结论**：DRAM 8.7%（数据在缓存里）、SM 18.4%（算术单元不忙）、L1 81.3%（访存端口快满了）
→ **卡在「访存指令的条数」，不是数据在哪，也不是算得多不多。**

**已提炼成一条要记的**：

> **「memory-bound」不是一层。**
> ```
> DRAM-bound    → 数据要去的次数太多（AI 低）
> L2-bound      → 数据在 L2 层就卡住了
> L1-bound      → 指令太多，端口不够（本次）
> 延迟受限       → 每次都要等，并行度不够藏
> ```
> **四堵墙，四种改法。只看「memory-bound」这个词做判断，会开错药。**

3. **「pdh_demo 没有任何记忆」** —— **最要命的一条**：

**根因**：和 11-23 的「填鸭」是同一个问题，只是换了个领域。

**已改的教学流程：**

4. 学员自己拼装——拼错了编译报错，那是好事

**关键区别：第 3 步给的是「工具箱」，不是「做好的椅子」。**

## 三、PDH 重装（用新方法）

### 第一层：系统里发生什么（无代码）

**核心讲清了一件事**：性能计数器给的是**累计值**，不是当前值。

```
第一次采：pid 4536 的 3D 引擎累计运行 1,000 ms
第二次采（1 秒后）：累计运行 1,047 ms
→ 这一秒用了 47 ms → 利用率 4.7%
```

**这才是「要采两次」的真正原因。** 学员之前只记住了动作，不知道理由。

**顺带纠正一个误解**：显存是**瞬时型**（采一次就够），只有利用率是速率型。

### 第二层：程序要做哪几件事（学员复述）

学员答：「订阅 → 采一次 → 等 1s → 再采一次 → 取实例 → 算差值 → 合并 → 显示」

**一处错误**：他把「采两次」放进了循环。已纠正：

```
       1000ms      2000ms      3000ms
         │           │           │
      采样A        采样B        采样C
         └──差值AB───┘
          第 1 帧
                     └──差值BC───┘
                      第 2 帧
```

**一次采样同时是「上一段终点」和「下一段起点」。所以循环里只采一次。**

### 第三层：函数表（只给名字和参数，不给代码）

学员的第一次填空：**12 个参数对了 7 个**，结构全对（七个调用的顺序一次排对）。

**五处错，其中四处是同一个原因——漏了 `&`。**

**已给一条能推的规则**：

| 前缀 | 含义 | 传什么 |
|---|---|---|
| 无 | 值 | 直接传 |
| **`LP`** | **指针**（Long Pointer） | **`&变量`** |
| `PP` | 结构指针 | 数组或 `&指针` |
| `H` | 句柄 | 句柄本身 |

> **「哪些参数要 `&`」不用背——看名字前面有没有 `L`/`P`。**

### 第四层：聚合（学员自己写）

**先问了「为什么利用率取 max、显存取 sum」**，学员答对了核心，但用了「共用」这个词。

**已纠正为**：

> **比例取 max，绝对量取 sum。**
> 不用记「哪个并行哪个独立」，只问一句：**这个数有单位吗？**
> 利用率 = 百分比（无单位）→ max；显存 = 字节（有单位）→ sum。

**学员写聚合时犯的核心错误**：把两个数组当成平行的

```cpp
for (DWORD i = 0; i < itemCount; i++) {
    ... items[i] ...        // 利用率，270 条，每进程每【引擎】一条
    ... memItems[i] ...     // 显存，150 条，每进程每【GPU】一条
}
```

**已讲清**：两个数组**长度不同、顺序不同、含义不同**，必须两个独立循环。

**另外三个小错**：`wcsstr` 第二个参数空着、`gpu[gp] = items[i]` 用了错的数组、
`it->second +=` 应该是 `git->second +=`。

**顺带教了一个简化**：求和不需要 `find/end`，`map[pid] += x` 直接对
（`operator[]` 在 key 不存在时自动插入默认值 0）。**只有取 max 才需要先查。**

重建后的 `pdh_demo.cpp` **76 行**（原注释版 250 行），编译通过、运行正确。

**学员自己说「对上了」。**

## 四、ETW 起步（第 1-2 步完成）

### 概念已讲

```
Provider（发事件的） → Session（内核里缓冲） → Consumer（你的程序）
     用 GUID 标识         有名字，全局唯一        从会话里读
```

**和 PDH 的根本区别：**

| | PDH | ETW |
|---|---|---|
| 数据形态 | 当前值（快照） | **事件流**（带时间戳的记录） |
| 谁主动 | 你问它 | **它来找你**（回调） |
| 有状态吗 | 无 | **有会话**（不清理会残留） |
| 权限 | 普通用户 | **内核 provider 要管理员** |

### 分四步走，每步独立验证

```
第 1 步  骨架（头文件 + 空回调）        ✅ 编译通过
第 2 步  会话开/关/清残留               ✅ "session start" / "session stop"
第 3 步  启用 provider                  🔶 代码写完，未验证
第 4 步  接上回调                        ⬜
```

### 学员踩的坑

**① `StartTrace failed: 5`** —— 错误码 5 = `ERROR_ACCESS_DENIED`。
**ETW 的实时会话需要管理员**（PDH 不需要，因为 PDH 读的是公开的汇总数据，
ETW 订阅的是内核内部的过程）。

**② 缺了「清残留」和「错误路径停会话」**

- 没写 `ControlTraceW(0, NAME, props, STOP)` —— 会话残留时下次会报 183
- `EnableTraceEx2` 失败时直接 `return 1`，**会话已经启动却没停** → 泄漏

**已提炼**：

> **两个 `return 1` 的区别：**
> `StartTraceW` 失败 → 会话没起来，不用停
> `EnableTraceEx2` 失败 → 会话已经在跑，**必须停**
>
> **判断依据是「这个时刻资源到底有没有被创建」。**

**③ 问「`Sleep(15000)` 有必要留吗」**

**已答**：它是**临时脚手架**，为了让会话活 15 秒好在另一个窗口用 `logman query -ets` 验证。
第 4 步接上 `ProcessTrace` 之后删掉——因为 `ProcessTrace` 本身就是阻塞的。

**并顺手讲了一个重要区别**：

| 资源 | 进程退出后 |
|---|---|
| `OpenProcess` 的句柄 | 系统自动回收 |
| `cudaMalloc` 的显存 | 系统自动回收 |
| **ETW 会话** | **不回收，会残留** |

**这是学员遇到的第一个「必须手动收尾、否则会污染系统」的资源。**
