## 三个 bug 的精确诊断（学员明天修，我不代写）

### bug 1 · reduction_v3：树归约少跑一步，丢了半块数据

```c
for (int s = blockDim.x / 2; s > 32; s /= 2)   // ← s=128、64 两步后结束
```

s=32 那一步被 `s > 32` 跳过 → tile[0..31] 各只含 16 个元素，tile[32..63] 的数据
**从未进入归约**。block 覆盖 1024 个元素，只归约了 512 个。
**修复方向**：循环条件要包含 s=32 那一步（`s >= 32`），或先把 tile 归到 32 再 shuffle。
证据链：sum=3.0 是「某 512 个元素子集」的和，而非全量。

### bug 2 · reduction_v6：atomicAdd 违反 harness 契约，结果 ×4

```c
if (lane == 0) atomicAdd(out, sum);
```

`reduction_common.h` 的 harness **launch 4 次**（预热 1 + 计时 3），且只在循环前
`cudaMemset` 一次。v0-v5 用 `out[...] = v`（幂等写）所以 4 次无害；v6 的 atomicAdd
**累加 4 次** → sum = 4 × ref = -20。**rel_err = 3.00 恰好等于 (4-1)/1**，铁证。
**修复方向**（任选）：① harness 每次 launch 前 memset（影响所有版本的计时口径，
不推荐）② v6 改成 block 级写回后再由主机汇总（和 v5 同构）③ 单独为 v6 处理。
注意：这是「kernel 与 harness 的契约」问题——harness 要求幂等写回，白天讲
v6 时应该把这个契约再点一遍。

### bug 3 · scan_v2：Hillis-Steele 是包含式，对拍要排除式

`scan_v2_local` 的 warp scan 产出**包含式**前缀和（`x` = 从头到自己的和），
而 `scan_common.h` 的对拍是**排除式**（expect = 前面所有元素的和，不含自己）。
整体错一位。
**铁证**：bad_count = 224,695，通过的 37,449 ≈ 262,144 ÷ 7——**恰好等于 a[i]=0
的元素个数**（a[i] = (i%7)-3，i%7==3 时 a[i]=0，包含式和排除式碰巧相等）。
**修复方向**：把包含式转排除式的标准做法——输出前一位的值
（`__shfl_up_sync` 换位 + 块首补 0），或在 warp 层用 carry 传递。
