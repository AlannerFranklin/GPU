## 二、第 13 周开始：归约七版

场地：`code/12-reduction/`。旧文件 `reduction.cu`（11-05 写的）已 `git rm`，
内容演进为 `reduction_v0.cu`。

### 2.1 文件结构

```
reduction_common.h    计时 + 对拍（从 matmul_common.h 改签名而来）
reduction_v0.cu       基线：shared 树形
reduction_v1.cu       展开：s ≤ 32 后只用一个 warp
reduction_v2.cu       每线程 4 个元素（跨步读）
reduction_v3.cu       最后 32 个改用 warp shuffle
reduction_v4.cu       整棵树干掉：8 个 warp 各自 shuffle，shared 只留 8 个 float
reduction_v5.cu       float4 向量化
reduction_v6.cu       atomicAdd 单 kernel 收尾
```

### 2.2 harness 的两处设计要点（已讲）

**① 输出 buffer 大小是 `grid.x`，不是 1。** 不同版本输出形状不同（v0-v5 每 block 一格，
v6 只写 `out[0]`），所以用 `cudaMemset` 清零 + 主机端无条件全加，兼容全部形态。

**② matmul 那边不用 memset 是因为 kernel 全覆盖写。** 已讲清判据：
**「这块内存在被读之前，是不是保证每个字节都被写过」**——matmul 保证，reduction 不保证。

### 2.3 基线分析（学员自己数的）

v0 的 `__syncthreads()`：`s = 128,64,32,16,8,4,2,1` 共 **8 次**
（他一开始答「8 × 4 个 block = 32 次」，把 block 并行当成了串行累加）。

八轮的有效线程-轮次：

```
128+64+32+16+8+4+2+1 = 255
255 ÷ (8 × 256) = 12.45%
```

**结论：树形归约的加法次数是最优的（N−1），但并行度指数衰减，96.5% 的线程-轮次在空转。**

### 2.4 学员犯的四个错（三个是「复制后没改」）

| 版本 | 错 | 后果 |
|---|---|---|
| v1 | `__syncthreads()` 写在 `if (threadIdx.x < s)` 里 | **内核挂死**（部分线程永远不到 Barrier） |
| v3 | 旧的 `out[..] = tile[0]` 没删，盖掉了 shuffle 的结果 | 静默错误，结果小约 64 倍 |
| v5 | 中间两段（warp shuffle + 写 warp_sums）整段丢失 | `warp_sums` 从未被写，读到垃圾 |
| v2 | kernel 名和 main 里的调用名仍叫 `reduction_v1` | 能编能跑，但版本混淆 |

**已立规矩：从一个版本改到下一个版本，先检查「哪些段落要删」，再检查「哪些要加」。**
（v3 和 v5 都是「加了新代码但没删旧代码 / 少抄了一段」，与 11-16 的「框架没改」是同一类毛病。）

### 2.5 讲到的并发概念

- **Barrier 不能放在发散分支里**：`__syncthreads()` 要求 block 内全部线程到达；
  判断条件里出现 `threadIdx` 就危险（`blockIdx` 是全 block 一致的，安全）
- **Volta 之后 warp 内不再严格锁步**，所以 warp 内同步要用 `__syncwarp()` 而不是 `volatile`
  （Harris 2007 那套 `volatile` 写法是 Tesla 时代的）
- **`__shfl_down_sync(mask, v, off)`**：线程 i 拿到线程 i+off 的 v；mask 全 1 表示 32 个全参与
- **warp 内归约的 off 从 16 起**（不是 32），因为 warp 里最大只有 31 号线程
- **第二次归约（8 个值）off 从 4 起**，且必须写 `(lane < 8) ? warp_sums[lane] : 0.0f`
  ——既防越界，又保证 32 个线程全员参与 shuffle
- **`atomicAdd`**：普通 `+=` 是读-改-写三步，多 block 同时做会丢；原子操作在硬件上不可分割

### 2.6 已预告的 v6 现象

v6 大概率比 v5 慢，两个原因（**都不是 bug**）：

1. **测量边界**：harness 只计 kernel 时间。v0-v5 的主机端求和发生在计时结束之后，
   v6 的原子加发生在 kernel 内部
2. **原子竞争**：10240 个 block 抢同一个地址，硬件串行化

## 三、今晚回家必做

```bat
build.bat 12-reduction run 10485760
```

**N = 10485760 = 10240 × 1024**，七版同一个 N 才能横向比。

| 优先级 | 检查什么 | 判定 |
|---|---|---|
| ① | 七个 `rel_err` | 全部 < 1e-3。**任何一个大了，那一版有 bug，性能数字无意义** |
| ② | 七个 `sum` | 应基本相同（浮点顺序差异在 1e-3 内） |
| ③ | `min_ms` 曲线 | 预期 v0 > v1 > v2 > v3 ≈ v4 > v5，v6 可能回升 |

**另有一个分析作业**：算 v0 的 AI

```
FLOP  = N = 10,485,760
字节  = 41.9 MB（读 N 个 float）
AI    = 10,485,760 ÷ 41.9e6 = 0.25 FLOP/byte
```

比 matmul 低两个数量级 → 必然是 memory-bound，且离带宽天花板极远（每次读只做一次加法）。
