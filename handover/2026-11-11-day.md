### 2. occupancy 算术（七步链条，学员已通）

先被问的三道题，**第 1 题对，第 2、3 题都算错**：

- 第 1 题 `65536 ÷ 80 ≈ 819` ✅
- 第 2 题 他答 `1024 × 80 = 18,432` ❌ —— 把 80 拆成了 `10 + 8`，实际算的是 `1024 × 18`
- 第 3 题 结论「启动不了」✅，但算式 `64*80=640+512=1152` 双错：
  ① 80 里已经包含那 64 个累加器，不能再用 64 去乘；② 64×80=5120 不是 1152

**正确答案：`1024 × 80 = 81,920 > 65,536` → 一个 block 就超了整个寄存器文件 →
`CUDA error: too many resources requested for launch`**

⚠️ **这是一个需要盯的习惯：他心算会漏。** 同类事故还有 GFLOPS 打成 2027（应为 2727）。
以后凡是手算，都要求他把每一步写出来，不接受心算结果。

拆成七步后他通了（SM 四条硬指标 → 单线程寄存器数 → 单 block 总量 → 两个上限取小 → occupancy）。

### 3. block 形状已定：`block(32, 8)` = 256 线程

**理由（已讲）**：`blockDim.x` 必须是 32，这样一个 **warp 恰好是「tx = 0..31，ty 固定」**，
跟他现有 tiled 版做 bank 分析时的模型完全一致。用 `block(16,16)` 会让一个 warp 横跨
ty=0/ty=1，之前记的规则全部失效。

**4×4 先行的理由（已讲）**：

```
16 累加器 + 4 A片段 + 4 B片段 + 约 10 杂项 ≈ 34 寄存器/线程
256 × 34 = 8,704 /block
65536 ÷ 8704 = 7.52  → 寄存器允许 7 个
1536 ÷ 256  = 6      → 线程数允许 6 个
min(7,6) = 6 个 block/SM × 256 = 1536 线程 = 100% occupancy
```

对照 8×8（80 寄存器/线程）：`256 × 80 = 20,480 → 3 个 block → 50% occupancy`。
**先 4×4 跑通量到数，再上 8×8 看掉一半 occupancy 换多少。一次只改一个变量。**

### 4. tile 尺寸已定：**32 行 × 128 列**

推导已讲通，学员自己复述正确：

```
行 = blockDim.y × TM = 8 × 4 = 32
列 = blockDim.x × TN = 32 × 4 = 128
32 × 128 = 4096 = 256 线程 × 16 输出 ✓
```

**N=4096 时 grid(32, 128) = 4096 个 block —— 学员自己算对了。**

## 二、卡住的地方（明天从这里接）

讲到「谁算哪 16 个」时，两条公式已经给出：

```
行：row_i = blockIdx.y × 32 + ty × 4 + i        i = 0..3
列：col_j = blockIdx.x × 128 + tx + j × 32      j = 0..3
```

其中**列的公式带一段完整的 bank 分析**（切法 (a) 连续 4 列 → 4 路冲突；切法 (b) 隔 32 跨 4 列 → 无冲突），
并给了生成规则：

> `Bs[k][c]` 的 bank = `c % 32`（因为 128 是 32 的倍数，k 那一项被模掉了）。
> 一个 warp 里 tx = 0..31，所以 `c` 必须让 32 个线程落在 32 个不同 bank 上。

**然后出的验证题他答不出来**：

> `blockIdx = (2, 1)`、`ty = 3`、`tx = 5`，这个线程负责 C 的哪 16 个位置？

**正确答案（明天直接可以用）：**

```
行：blockIdx.y × 32 + ty × 4 + i = 1×32 + 3×4 + i = 32 + 12 + i = 44, 45, 46, 47
列：blockIdx.x × 128 + tx + j×32 = 2×128 + 5 + j×32 = 261, 293, 325, 357
```

**判断**：他原话「不知道，这块我算不明白了」。
这不是数学问题，是**三层坐标同时出现**（blockIdx 一层、ty/tx 一层、线程内 i/j 一层），
一次性记住三层超出了他当前的工作记忆。他自己提出「得做一个专题，明天仔细学习」——**判断正确，采纳**。

## 三、明天怎么做（专题：三层坐标映射）

**不要接着往下讲 shared 怎么填、循环怎么写。先把坐标映射单独拆开练透。**

建议做法：

1. **用最小具体例子**，别用 N=1024/4096。取 `N = 256`、`block(32,8)`、`grid(2,8)`、共 16 个 block。
2. **把 C 画成带真实下标的表格**（不是抽象的 `row_i`），标出每个 block 的 32×128 边界。
3. **只追一个线程**：`blockIdx=(1,0)`、`ty=2`、`tx=7`，在图上圈出它那 16 个格子，
   让他自己念出 16 个下标。
4. 再换 2~3 个线程重复，直到他能在图上直接指出来。
5. **最后才回到公式**，说明公式只是这张图的压缩写法。
6. 通了之后再往下走：shared 怎么填（`As[32][32]` 不变、`Bs[32][128]` 是新的）、内层循环怎么写。

**注意**：他心里有一条现成的规则「`[行][列]`，ty 管行、tx 管列」（见 memory `unified-rules-over-cases`）。
这次要新增的是**第三个维度：线程内部那 4 行 4 列**。必须明确告诉他这条总规则怎么扩展到三层，
**不要让他以为是另一套平行规则**——否则会和原来的互相污染。

## 四、已经定下来的设计规格（明天直接用，不用重推）

```
block        : block(32, 8) = 256 线程
每线程输出    : TM × TN = 4 × 4 = 16 个
block tile   : 32 行 × 128 列
寄存器        : acc[4][4] + a[4] + b[4] + 杂项 ≈ 34 个/线程
occupancy    : 6 block/SM = 1536 线程 = 100%
shared       : As[32][32]（跟 tiled 版一模一样，不用改）
               Bs[32][128]（列数从 32 涨到 128）
外层 k 循环   : for (t = 0; t < N/32; t++)   ← 跟 tiled 版一致，不变
行映射        : row_i = blockIdx.y*32 + ty*4 + i
列映射        : col_j = blockIdx.x*128 + tx + j*32   ← 必须隔 32 跨，否则 4 路 bank 冲突
Bs bank 规则  : bank = c % 32，c 必须取 tx + j*32
C 写回        : C[row_i * N + col_j]，warp 内 32 个线程写 32 个连续 float = 128B，完美合并
```

**尚未确定/尚未讲的**：shared 填充阶段的线程与元素映射、内层循环结构、`__syncthreads()` 位置
（应该和 tiled 版一样是两处，但填充的循环写法要重新设计，因为现在 256 线程要填 32×32 和 32×128）。
