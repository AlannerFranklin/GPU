# 10-cuda 笔记：合并访存实测与 ratio=11.31 的拆解

> 2026-11-05 晚，4070 Ti Super + nvcc 12.6。对应 ROADMAP 第 10 周。
> 实验代码：`vector_add.cu`（`vector_add` 合并版 vs `vector_add_strided` 散开版）。

## 实验数据

N = 1e6，int 数组 a / b / c 共 **12MB**（读 8MB + 写 4MB），L2 = 48MB，数据整个装得进 L2。

| kernel | min 耗时（3 轮取最小） | 有用带宽 | 备注 |
|---|---|---|---|
| vector_add（合并访存） | 0.006880 ms | **1744 GB/s** | 超过 DRAM 峰值 672 GB/s → 测得是 **L2 带宽** |
| vector_add_strided（散开） | 0.077824 ms | **154 GB/s** | 每 32B sector 只有 4B 有用 |

**ratio = 11.31**（strided_min / coalesced_min）

## 为什么是 11.31，而不是理论值 8

### 第一步：交易模型给出理论值 8

- GPU 访存最小交易单位是 **32 字节 sector**
- 合并版：warp 的 32 线程读连续 32 个 int = 128B = **4 个 sector**，效率 100%
- 散开版（`i = threadIdx.x * gridDim.x + blockIdx.x`，相邻线程地址差 3907 个 int）：
  32 个线程落在 **32 个不同 sector**，每笔 32B 只用了 4B，效率 12.5%
- 流量比 = 32 / 4 = **8**

### 第二步：96MB 的算术

```
有用数据 = 12MB（a 读 4MB + b 读 4MB + c 写 4MB）
散开版每 4B 有用数据都装在 32B 的 sector 里 → 交易膨胀 8 倍
交易总量 = 12MB × 8 = 96MB
```

### 第三步：8 × 1.4 ≈ 11.31

ratio 是**时间比**，不是流量比。除流量差 8 倍外，还有第二层损耗：

- 合并版：96MB 之外的额外损耗为零，12MB 交易 ÷ 6.88µs = **1744 GB/s**（L2 sector 吞吐）
- 散开版：96MB 交易 ÷ 77.8µs = **1234 GB/s** ← 同样的 L2，吞吐掉了 1.4 倍
- 原因：L2 每周期能"接单"的数量有限，散开版每 warp 要下 **32 笔单**（合并版只 4 笔），
  队列排长，单位时间服务的总字节数下降

**结论：11.31 ≈ 8（读写双向的流量浪费）× 1.4（请求排队损耗）。**

### 第四步：11.31 是"温柔版"

12MB < 48MB L2，散开版的 96MB 交易全在 L2 完成，DRAM 没参与。
数据一旦超过 L2：合并版掉到 DRAM 带宽（~672 GB/s），散开版掉到 DRAM 随机访问
（几十 GB/s）——ratio 会**反升**到 20~30。所以 11.31 是下限，不是典型值。

## 一眼判断访存是否合并

只问一个问题：**相邻的 threadIdx，访问的地址相邻吗？**

| 索引写法 | 判断 |
|---|---|
| `i = blockIdx*block + threadIdx` | 相邻 ✅ |
| `i = threadIdx*grid + blockIdx` | 差 grid 个元素 ❌ |
| 二维：`col` 随 threadIdx.x 连续 → 行内连续 ✅；`row` 变化 → 跨整行 ❌ |

transpose.cu 的读 `in[row*N+col]` 合并、写 `out[col*N+row]` 散开——明天 transpose_shared
就是要把写也变成合并的。
