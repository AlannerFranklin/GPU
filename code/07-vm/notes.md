TLB是一个硬件结构，「转译后备缓冲器」Translation Lookaside Buffer，页表的缓存
缓存的是虚拟页号和物理页号的对应关系

命中就直接拿到物理页号，没命中就会从内存中读取页表，把结果写回TLB

一条TLB表项存的是2个页号+几个标志位，十几字节

TLB 是 CPU 里的一个小容量高速缓存，缓存的是虚拟页号 → 物理页号的映射。命中就直接拿到物理页号，不用查内存里的页表；没命中就由硬件走一遍 4 层页表，再把结果写回 TLB。本机 L1 约 256 到 512 条，L2 约 2048 到 4096 条——这是把工作集从 64 KB 逐次翻倍到 256 MB，看每次访问耗时在哪一级突然跳上去测出来的。

795ns花在
① 停下当前指令，保存现场，跳进内核
②   快路（你的实验走的就是这条）：空闲页框链表里还有货，直接摘一页，几十纳秒
    慢路（内存耗尽）：要从别的进程那儿抢一页，如果那页被改过，还得写回磁盘——那一次是几毫秒，不是 795 ns
③ 清0所选的物理内存
④ 记录物理页号，写进页表
⑤ 恢复现场，重新执行那条触发缺页的指令

1. 进程隔离是靠什么做到的？（提示：不是靠软件检查）
直接分配不同的物理内存，同一个虚拟地址映射到不同的物理内存中。靠每个进程各自一张页表，由 MMU 硬件按当前进程的页表做地址翻译。同一个虚拟地址在两个进程里查到两个不同的物理页号，所以落到不同内存。
2. 同一个进程里的两个线程，哪些东西共享、哪些各自独立？各举两样。
页表，虚拟地址空间，全局变量/堆，文件句柄共享，栈，寄存器各用各的
3. 为什么进程切换比线程切换贵？用你测过的 TLB 来解释。
进程切换要把 CR3 改成指向另一个进程已有的那张页表，TLB的旧映射全部作废，重新建立TLB，接下来的几千次访问都会是TLB未命中。
4. 你的上位机里，如果采集线程和 UI 线程共用一个 std::vector，会发生什么？为什么会这样？
如果采集线程在push_back，UI同时便利，会崩溃，因为线程不隔离，不够安全，一个线程写坏了内存，整个进程就崩溃了。
采集线程 push_back → vector 满了 → 扩容
    ① 分配一块 2 倍大的新内存
    ② 把旧元素搬过去
    ③ delete 旧内存          ← 关键在这一步
    ④ 成员指针改成指向新内存

UI 线程手里还握着旧的指针/迭代器
    ⑤ 遍历 → 读一块已经 delete 掉的内存 → 未定义行为
这叫悬垂指针
采集线程 push_back 触发扩容时会 delete 旧数组，UI 线程手里还握着旧指针，遍历就是读已释放的内存——悬垂指针，未定义行为。
